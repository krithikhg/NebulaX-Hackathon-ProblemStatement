# PS3 — Train Condition Monitoring (Team solution)

Two subsystems of PS3:

* **Rail Corrugation** — classify each 1-second, 10 kHz axle-box vibration/
  shock recording as **Normal**, **Side I** or **Side II** (metric: macro F1).
* **SHM** — regress a single cumulative-fatigue-damage value from a dynamic-
  stress time series (metric: `max(0, 1 − MAPE)`).

The sections below are grouped per subsystem.

# from the repository root

## Results (out-of-fold, 272 train files)

| metric | single model (12-seed mean) | seed-ensemble (pooled OOF) |
|---|---|---|
| macro F1 | 0.833 ± 0.029 | **0.880** |
| Side I F1 | 0.662 | **0.786** |
| Side II F1 | — | 0.875 |
| Normal F1 | — | 0.979 |

Confusion (seed-ensemble): Normal 229/234, Side I **11/14**, Side II 21/24.
Error anatomy: 5 missed detections, 5 false alarms, only **1 side swap** — the
task is fault-vs-Normal detection, not side localisation. Per speed band,
recall is 0.90 at 35–60 km/h but 0.71 at 60–90 km/h (the Side I signature
collapses at high speed; see below).

## Approach

1. **Speed / order normalisation.** The `Rotating speed` column is a raw
   90-tooth toggle; speed is derived from rising-edge intervals and used to
   (a) resample signals into the wheel-angle domain (order tracking) and
   (b) define a speed-adaptive corrugation band (`v/0.5 … v/0.03` Hz for
   wavelengths 3–50 cm).
2. **Features.** Per-channel time stats and Welch band energies aggregated per
   side; per-car localisation summaries; amplitude-invariant *shape* features
   (normalised spectra, spectral entropy/flatness); true 64-channel
   per-position summaries; spectral-kurtosis, autocorrelation periodicity and
   wavelet-packet (T7) features.
3. **Model.** Flat 3-class LightGBM (regularised defaults) on the **top-40
   features selected by importance**, averaged over 10 seeds.
4. **Metric-aware evaluation.** Stratified 5-fold CV, mean-of-seed reporting,
   per-class and per-speed-band breakdowns.

## Validation methodology (no leakage)

* 272 labelled `Train/` files for development; 68 unlabelled `Test/` inputs for
  final inference only. Test **labels are never available**; test inputs are
  never used for training, feature selection or thresholding.
* **Stratified 5-fold CV** (not a single split) because Side I has only 14
  examples. Every reported number is out-of-fold.
* Feature selection and augmentation are done **inside each fold**; features are
  computed per file with no cross-file statistics. The final model re-selects
  features on all train data (standard), while the honest estimate keeps
  selection in-fold.
* Model choices were compared on mean-of-seed CV; a few configs that looked
  better on one pooled split were rejected when they failed across seeds.

## Investigated and rejected (documented, code archived)

Speed augmentation (synthetic slow faults), side-symmetry/mirror
augmentation, hierarchical Normal→Side, a binary detector with a macro-F1-tuned
threshold, decision-boundary calibration, class weighting, curve/coherence
proxies, order-domain phase/wave-propagation features, and two deep-learning
tracks (side-aware 1D-CNN and STFT 2D-CNN). None beat the feature-based
LightGBM; the ceiling is set by 14 Side I examples whose signature overlaps
Normal at running speed and disappears above 60 km/h.

## SHM — cumulative fatigue damage

The target is a single damage number per file, computed by the organisers with
**Miner's linear damage rule** (rainflow counting + an S-N curve) applied to the
raw dynamic-stress series (~581k samples). The mapping is therefore
*deterministic*, so the correct approach is to **reproduce the calculation and
calibrate its constants**, then refine with a physics-informed regression — not
to learn it blindly from generic features.

```bash
cd PS3/subsystems
../../.venv/bin/python -m shm.predict      # writes shm/predictions/shm_predictions.csv
../../.venv/bin/python -m shm.benchmark    # physics vs ML vs residual comparison
../../.venv/bin/python -m shm.report_figs  # figures -> shm/figures/
../../.venv/bin/python -m shm.ablate_stream                 # online vs batch counter
../../.venv/bin/python -m shm.stream_watch --input <dir> --stream "Train 01 / bogie"
```

### Method

1. **Rainflow count** with `fatpack` using **`k = 64` load classes**. `k = 64`
   is a sharp, isolated optimum against the reference labels across
   `k = 8…1024`, so we treat it as the organisers' counter.
2. S-N curve `N = C / σₐᵐ` + Miner's rule give `D = k · Σᵢ nᵢ·rangeᵢᵐ` (the `2ᵐ`
   amplitude factor is absorbed into the scale `k`). The counter yields one
   cycle per range, so `S(m) = Σ rangeᵐ` is the pseudo-damage.
3. **Analytic baseline** — fit the two global constants on the 64 training
   labels by minimising MAPE: `k` has a closed form (a weighted median), leaving
   a 1-D grid search over `m` → `m = 5.00`, `k = 4.06e-11`.
4. **Shipped model — physics-informed Ridge** — regress `log D` on the bank
   `[log S(m) for m = 3.0…7.0]`, i.e. learn the S-N curve shape instead of
   assuming a single exponent (standardised + `RidgeCV`).

### Results (8-fold CV, 5 seeds; everything refit in every fold)

| method | CV MAPE | score `1 − MAPE` |
|---|---|---|
| constant median | 91.5% | 0.08 |
| Ridge, generic time + spectral features | 18.7% | 0.81 |
| analytic physics (`m = 5.00`, `k = 4.06e-11`) | 0.88% | 0.991 |
| physics + residual Ridge | 0.69% | 0.993 |
| **physics-informed bank Ridge (shipped)** | **0.55%** | **0.9945** |

The analytic model recovers the textbook steel exponent `m = 5.00`; the
physics-informed Ridge refines it (learned weight profile in
`figures/shm_05_bank_weights.png`) and is robustly better — +0.32 pp over the
analytic model, improving **150/160** nested folds.

### Why is it not 100%?

The reference label is a deterministic function of the stress series given the
organisers' formula *and their exact tooling*, so an exact reproduction would be
exact. The residual is **not random noise**: it is multiplicative (slope of
`log(D/S)` on `log D` ≈ 0), and it shrank dramatically once the counter matched —
per-file `D/S` spread fell from **4.1%** (the `rainflow` package) to **1.3%**
(`fatpack`, `k = 64`). It is therefore dominated by small *implementation*
differences (the exact load-class/bin convention and residue handling in the
rainflow step), not by a stochastic component. We also confirmed there is no
additive label noise and that mean-stress corrections make it worse.

### Validation (no leakage)

* 8-fold CV over the 64 labelled train files, repeated over 5 seeds; the
  constants **and the Ridge** are refit inside every fold. The 16 test inputs
  are used for inference only — never for fitting or selection.
* The generic-ML benchmark deliberately **excludes the physics feature** so the
  comparison is fair. Spectral features help the *generic* baseline
  (22.4% → 18.7%) but are irrelevant once the rainflow feature is present —
  evidence that the physics insight, not the algorithm, is what matters.
* Counter choice was validated by nested CV, not a single split: `k = 64` beat
  its neighbours (0.79% vs ≥1.1% MAPE) and `fatpack` beat `rainflow`'s ASTM count
  at every setting.

### Investigated and rejected

* `rainflow`-package counter (2.5% MAPE) → replaced by `fatpack` `k = 64`
  (0.8%): the single biggest gain, driven by matching the organisers' tooling.
* **Mean-stress (Goodman) correction** and **fatigue-limit cutoffs** — the
  former made results worse, the latter changed nothing, confirming the labels
  use a plain `rangeᵐ` sum.
* **Detrending** each series before counting — worsened MAPE (0.8% → 1.6%).

### Cumulative / real-time monitoring

Beyond the per-segment score, the solution tracks **cumulative** Miner damage per
monitored stream (train / measurement point, free-text label). Miner's rule is
additive, so the running state is a tiny Markov summary
(`D`, `n_segments`, `n_samples`, `rate`) persisted in Cloud Storage (or a local
file). The app shows a live D / remaining-life dashboard with a fleet view, and
`shm.stream_watch` auto-ingests a folder of segments with threshold alerts.
A single-pass streaming counter is implemented and ablation-tested
(`shm.ablate_stream`); it trades accuracy for bounded memory, so the exact
per-segment counter remains the shipped model. See `shm/METHOD.md` §6.
